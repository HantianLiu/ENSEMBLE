Project ENSEMBLE：面向普通读者的项目概述
版本：v0.7.0 历史概述
更新时间：2026年9月22日
当前软件发行版：v0.7.5；请以 README.md 与 README_v071.md 为准。


一、这是什么？

Project ENSEMBLE 不是一个新训练出来的“大模型”，而是一套组织多个现有人工智能模型共同工作的会议系统。

可以把它想象成一间有明确议事规则、主持人、资料室、密封投票箱和会议档案的“数字会议厅”。不同模型不只是轮流聊天，而是在相互隔离的条件下提出意见、提交修正案、查阅证据、投票，并把全过程保存为可以复查的记录。

项目希望解决的核心问题是：如果一项复杂任务不能放心交给单个模型，怎样让多个模型在不轻易相互迎合、不提前串通、不过度依赖记忆的情况下，共同形成一份可解释、可追踪、可恢复的结果？


二、为什么不直接让几个模型自由讨论？

自由讨论看起来简单，但容易出现几个问题：

- 后发言的模型可能只是附和前面的意见；
- 一个很有把握但事实错误的回答，可能迅速影响所有参与者；
- 少数意见和反对理由容易在总结时消失；
- 中途失败后，很难判断哪些工作已经完成、哪些需要重做；
- 最终文本往往无法说明某项结论来自谁、经过了什么程序、依据了哪些资料。

ENSEMBLE 因此采用“先独立、后公开；先冻结、再汇总”的思路。需要独立完成的内容会先密封收集，等所有参与者提交后再统一公开。这样做更像正式评审或委员会会议，而不是多人聊天室。


三、会议中有哪些角色？

1. Representative（代表）

代表负责提出方案、审阅文本、提交修正案和参加表决。同一个基础模型可以承担不同职能，但每个代表拥有独立的会议身份和上下文，不能读取其他代表的私有文件。

系统目前使用四种面向人的职能名称：

- Builder / 建构者：关注整体结构、依赖关系、接口和内部一致性；
- Monitor / 监管者：关注复杂度、成本、可执行性和系统是否能够稳定维持；
- Cartographer / 制图者：绘制可能的方案空间，寻找尚未被考虑的可行路径；
- Librarian / 智库长：关注定义、知识边界、证据链、假设和待验证问题。

这些名称表示工作视角，不是虚构人物，也不要求模型进行角色扮演。

2. Chair（主席）

主席负责主持程序，而不是作为额外代表参与竞争。主席整理议程、判断修正案之间的依赖或冲突、执行投票规则、把通过的修改写入新稿，并在最终阶段向人类报告会议情况。

如果制度本身没有说明某个程序冲突应该怎样处理，主席不能自行发明规则。系统会暂停并向人类提出一个具体问题；人类也可以在命令行中要求主席用自然语言解释该程序问题。

3. Research Desk（文献调研台）

文献调研台是共享的外部知识服务，不是代表，也没有投票权。它把具体事实主张转化为可检索的问题，搜索学术论文、正式标准、官方资料及必要的网页材料，并整理成结构化证据包。

它不仅寻找支持材料，还必须主动寻找反证、适用限制和其他解释。它回答的是“公开资料对这个问题提供了什么证据”，而不是“会议最终应该支持哪个方案”。

4. Human（人类使用者）

人类决定会议类型、使用哪些模型、推理强度、是否启用联网调研，以及任务是什么。人类保留最终控制权，可以处理中途的制度冲突，也可以在会议需要介入时收到通知。

5. 独立审阅与审计角色

实体文本完成后，系统可以组织独立的知识完整性审阅，并保存不同审阅者的意见。代表还会在会后明确说明是否请求进一步审计。完整的 Audit Conference（审计会议）仍有部分规则处于开发或待决定状态，因此系统不会假装所有审计能力都已经完成。


四、一场普通会议怎样进行？

一次典型议事会议大致包括以下过程：

1. 初始化会议
   人类选择会议类型、模型供应商、具体模型、代表和主席的推理强度、是否启用文献调研，并输入任务描述。会议文件直接建立在启动命令所在的目录中。

2. 形成初稿
   系统随机选择一名合格代表起草第一版总则草案 D0。

3. 独立收集立场
   各代表分别审阅当前草案。所有立场完成前，系统不会把其中一人的正文提前展示给其他人。

4. 形成并处理修正案
   修正案被冻结并进入可重放的随机顺序。若两个方案互斥，系统会把互斥部分隔离为多选方案；不互斥的部分仍可分别表决。

5. 密封表决
   代表独立投票，部分票数不会提前公开。只有完整投票窗口冻结后才公布结果。达到规定门槛的修正案由主席写入下一版文本。

6. 多轮修订
   总则依次经历 D0→D1、D1→D2、D2→D3 三个窗口，并在最后进行总则批准表决。

7. 形成细则
   总则通过后，系统把任务拆成细化项目，选择主要起草人，形成细则草案 C0。代表对具体条款提出修改、拆分或暂停动议，并通过分组方案和必要的决选处理。

8. 独立审阅与出版
   主席进行程序认证，独立审阅者检查知识完整性和执行说明。系统把正式成果作为正文，把审阅意见作为附录，生成 Markdown 和可阅读的 PDF。

9. 会后述职
   主席向人类简要说明会议经过、主要争议、各代表的表现和审计请求情况。命令行显示短版报告，完整版本保存在会议目录中。


五、文献调研有什么不同？

启用 Research Desk 后，代表可以在提案、质疑和否决等关键阶段提交具体、可验证的事实问题。每轮请求先密封收集，再统一调研，避免某个代表因为先看到别人的问题而改变自己的请求。

调研结果形成 evidence packet（证据包），其中包括：

- 原始主张和规范化后的核验问题；
- 搜索范围；
- 支持证据；
- 反证或异议；
- 适用条件与限制；
- 常见替代解释；
- 仍未解决的问题；
- 来源信息、DOI、网址和归档文件；
- 当前知识状态，例如已有来源支持、需要限定条件，或仍无法解决。

所有已发布证据包构成本次会议的公共资料库。论文 PDF 和其他原始文档会被整理成可下载的文献包。为了避免模型上下文无限膨胀，单次调用只注入与当前议题最相关的有限视图；完整资料库不会因此被删除。

系统还支持“只召开文献调研会议”：不设置代表和主席，只对一个具体事实问题进行对抗性检索，并输出证据包和文献压缩包。

系统也支持从既有会议接续形成完整文献调研报告。新会议不会改写源会议，而是复制源会议
公开的证据包、调研轮次和文献原文，并保存逐文件哈希谱系。此时“总则”表示研究总纲：
四名分别担任建构者、监管者、制图者和智库长的规划代表独立提交问题拆分方案，每份最多
八个一级模块；主席完成可追溯聚类后，再由全体代表进行一次限量结构审阅。已经收集的
新鲜证据可以直接复用，只对后续确认的证据缺口重新检索。

冻结总纲之后，系统严格按模块顺序推进：轮换的四人组提出问题，Research Desk 检查现有
证据并处理顺序追问，再由建构者起草、其他三个职位专业审阅、全体代表限量审阅和 3/4
确认。无法取得 3/4 支持的模块仍会作为争议模块进入报告，并匿名并列反对意见。

全部模块完成后，随机抽取智库长撰写摘要、引言、方法、跨模块综合和结论；模块正文保持
冻结并机械插入。全文经一次全体审阅后无条件发表，不以代表票数判定事实真伪。事实性
反对意见与主席的可读性措辞修改均由全部智库长逐条审核。最终成果包括显眼位置的
Markdown、PDF、编号参考文献、未解决问题附录、审计清单和可下载文献包。

如果没有可以接续的源会议，也可以从零开始完整报告流程。此时不会伪造继承材料，系统
明确记录继承证据包数量为零，从空的会议级证据库开始形成研究总纲。


六、系统怎样提高可靠性？

1. 相互隔离
   代表只能看到当前阶段允许公开的材料和自己的记录，不能读取其他代表的私有状态、真实身份映射或未来阶段规则。

2. 密封窗口
   独立立场、投票和部分审阅在冻结前不公开，减少跟风和策略性迎合。

3. 留下证据链
   会议的重要事件写入只能追加的哈希链日志。系统还记录模型调用、文件访问、投票来源、文本版本和最终出版物的哈希值，便于事后核对。

4. 可以中断恢复
   会议按阶段保存结果。网络失败、终端中断或模型暂时不可用时，已经完整落盘的工作通常会保留；恢复时只重做缺失或不完整的部分。

5. 保守失败
   对没有明确规则的情况，系统倾向于暂停、保留异议或请求人类处理，而不是为了“顺利跑完”自行猜测制度答案。

6. 多供应商协作
   当前实现可以接入 DeepSeek、Kimi、GLM 和 Gemini 等模型。不同模型可以并行处理互不依赖的密封任务；同一模型的并发数受到明确限制。

7. 资源与上下文监测
   系统记录输入、输出、推理和缓存 token，显示缓存命中率，并在调用前检查输入上下文是否超过安全预算。大型文献数据库采用有界相关性视图，避免历史资料在每一轮无限累积。


七、人类最终能得到什么？

完成的会议通常会在会议目录最外层提供几个醒目的入口：

- FINAL_REPORT.pdf：适合直接阅读和传阅的最终报告；
- FINAL_REPORT.md：最终报告的纯文本源文件；
- CHAIR_BRIEF.txt：主席提供的执行摘要；
- CHAIR_DEBRIEF.md：主席会后述职；
- MEETING_RESULTS.md：主要结果和文件索引。

启用文献调研后，原始资料包保存在 public/research/literature_bundle.zip；只召开文献调研会议时，会议目录最外层还会提供醒目的 LITERATURE_BUNDLE.zip 入口。

正式结论、少数意见、知识审阅和审计请求彼此区分。审阅意见作为附录出现，不会悄悄改写已经通过程序认证的正文。


八、它适合什么任务？

ENSEMBLE 更适合以下类型的工作：

- 需要从多个角度审阅的复杂研究或技术方案；
- 需要保留反对意见和决策依据的制度设计；
- 涉及大量事实核验和文献来源的分析任务；
- 需要中断恢复、过程留痕和责任边界的长期模型协作；
- 希望比较不同模型供应商，而不是依赖单一模型的任务。

它不适合追求几秒钟内得到简单答案的场景。正式会议会调用多个模型、经历多轮冻结和表决，因此通常比普通聊天更慢、成本更高。


九、目前有哪些边界？

这是一个仍在发展的实验性系统，不是已经定型的自动治理产品。

- 多模型投票不等于事实必然正确；共同错误仍然可能发生。
- 文献检索能提高可追溯性，但不能保证公开资料本身完整或无偏。
- 一些细则划分、支持门槛和审阅流程仍明确标记为试行政策。
- 完整审计会议还有尚未实现或尚待人类决定的制度分支。
- 某些格式错误、规则冲突或供应商故障仍会让会议暂停。
- 系统不会替代人的法律、医学、伦理或组织责任。最终采用、拒绝或试行会议成果，仍由人类决定。


十、一句话总结

Project ENSEMBLE 尝试把“让多个大模型一起回答问题”，改造成“让多个受约束、相互隔离、能够查证资料的模型参加一场可恢复、可审计、由人类保留最终权力的正式会议”。

它最看重的不是让所有模型尽快达成一致，而是让结论如何形成、依据什么形成、有哪些反对意见以及哪里仍不确定，都能够被人看见和复查。
